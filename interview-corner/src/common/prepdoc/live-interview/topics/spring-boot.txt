1️⃣ Spring Boot Fundamentals (Must-Know)
1.	Why was Spring Boot created? What problems does it solve beyond Core Spring?
    1️⃣ Why Core Spring alone was painful in real projects
    Core Spring (Spring Framework) is powerful, but in real-world enterprise systems it introduced friction.
    ❌ Problems with Core Spring
    1. Excessive Configuration (XML / Java Config)
    ➡️ Problem: Too much boilerplate, slow onboarding.
    ________________________________________
    2. Dependency version Hell
    3. Manual Servlet Container Setup
    ➡️ Problem: Deployment complexity, not cloud-friendly.
    ________________________________________
    5. Slow Microservices Adoption
    ➡️ Problem: Spring felt heavy compared to newer frameworks.
    ________________________________________
    2️⃣ Why Spring Boot was created (the real reason)
    👉 Spring Boot was created to remove friction, not replace Spring.
    Spring Boot = Spring Framework + Opinionated Defaults + Production Readiness

2.	What does “opinionated defaults” really mean in Spring Boot?
    Opinionated defaults” in Spring Boot mean that the framework makes pre-chosen, sensible configuration decisions for you based on common industry practices, so you can start building applications with minimal setup—but you can override any of those decisions when needed.
    3️⃣ Concrete Examples (Very Important)
    Example 1: Web App
    Add this dependency:
    spring-boot-starter-web
    Spring Boot automatically:
    •	Starts Tomcat
    •	Registers DispatcherServlet
    •	Enables JSON serialization
    •	Configures exception handling
    👉 You did not ask for these explicitly
    That’s opinionated behavior.
    ________________________________________
    Example 2: Database
    Classpath contains:
    spring-boot-starter-data-jpa
    Spring Boot assumes:
    •	You want JPA
    •	You want Hibernate
    •	You want HikariCP
    •	You want transactions
    It auto-configures:
    •	EntityManagerFactory
    •	DataSource
    •	PlatformTransactionManager
    ________________________________________
    4️⃣ How Does Spring Boot Decide?
    Through conditional auto-configuration:
    @ConditionalOnClass(DataSource.class)
    @ConditionalOnMissingBean(DataSource.class)
    public class DataSourceAutoConfiguration { }
    Meaning:
    •	If DataSource is on the classpath
    •	AND you didn’t define one
    → Spring Boot defines it for you
    ________________________________________
    5️⃣ Opinionated ≠ Inflexible (Key Interview Point)
    You can override any opinion.
    Override via properties
    spring.datasource.hikari.maximum-pool-size: 30
    Override via custom bean
    @Bean
    public DataSource dataSource() {
        return new CustomDataSource();
    }
    Disable auto-configuration
    @SpringBootApplication(
      exclude = DataSourceAutoConfiguration.class
    )


3.	How Spring Boot reduces boilerplate compared to Spring?
    @Bean
    public DataSource dataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl(...);
        ds.setUsername(...);
        return ds;
    }
    @Bean
    public LocalContainerEntityManagerFactoryBean emf() { ... }
    @Bean
    public PlatformTransactionManager txManager() { ... }
    Spring Boot
    yaml
    spring.datasource.url=jdbc:mysql://...
    spring.datasource.username=root
    spring.datasource.password=pass
    ➡ 3–5 beans removed

    Why?
    Spring Boot scans the classpath
    Applies conditional auto-configuration
    Creates beans only if missing
    Spring Boot
    @SpringBootApplication
    Which internally enables:
    •	@Configuration
    •	@EnableAutoConfiguration
    •	@ComponentScan
    ➡ Multiple configs → one annotation
    6️⃣ No XML Configuration (Mostly)
    Spring Boot favors:
    •	Java config
    •	Annotations
    •	Properties/YAML
    server.port: 8081
    spring.jpa.show-sql: true
    No:
    •	web.xml
    •	applicationContext.xml
    •	dispatcher-servlet.xml
    Internal Mechanisms Behind the Scenes
    Spring Boot reduces boilerplate using:
    •	@ConditionalOnClass
    •	@ConditionalOnMissingBean
    •	@EnableAutoConfiguration
    •	spring.factories / AutoConfiguration.imports
    •	BOM dependency management

Conditional configuration:
    Conditions prevent unwanted bean creation and make Spring Boot’s auto-configuration possible.
    3️⃣ The Root Annotation
    All conditional annotations are built on:
    @Conditional
    It accepts a class that implements:
    Condition
    boolean matches(ConditionContext ctx, AnnotatedTypeMetadata md)
    If matches() returns true → bean/config is applied
    If false → skipped

    ________________________________________
    4️⃣ @ConditionalOnBean

    5️⃣ @ConditionalOnWebApplication

    DataSource Auto-Configuration
    @Configuration
    @ConditionalOnClass(DataSource.class)

4.	Difference between Spring Boot vs Spring Framework vs Spring Cloud.
    Big-Picture One-Liner (Very Important)
    Spring Framework is the core foundation,
    Spring Boot simplifies building and running applications,
    Spring Cloud solves distributed-system problems on top of Spring Boot.
    ________________________________________
    2️⃣ Spring Framework (Core Spring)
    What It Is
    •	The base framework for Java enterprise applications.
    •	Provides:
    o	IoC / DI
    o	AOP
    o	Transaction management
    o	Spring MVC
    o	Data access abstractions
    What It Solves
    •	Tight coupling
    •	Boilerplate enterprise code
    •	Cross-cutting concerns
    Key Characteristics
    •	Manual configuration
    •	High flexibility
    •	Steep learning curve
    Example
    @Bean
    public DataSource dataSource() { ... }
    When to Use
    •	Legacy enterprise apps
    •	Applications needing fine-grained control
    •	Non-Boot environments
    ________________________________________
    3️⃣ Spring Boot
    What It Is
    •	A convention-over-configuration layer on top of Spring Framework.
    What It Solves
    •	Too much configuration
    •	Slow project setup
    •	Inconsistent environments
    Key Features
    •	Auto-configuration
    •	Starter dependencies
    •	Embedded servers
    •	Actuator (health, metrics)
    Example
    spring.datasource.url=jdbc:mysql://...
    Internals
    •	Uses conditional auto-configuration
    •	Does NOT replace Spring
    When to Use
    •	Microservices
    •	REST APIs
    •	Cloud-native apps
    •	Rapid development
    ________________________________________
    4️⃣ Spring Cloud
    What It Is
    •	A set of tools for distributed systems, built on Spring Boot.
    What It Solves
    Microservice challenges:
    •	Service discovery
    •	Centralized configuration
    •	Load balancing
    •	Circuit breaking
    •	API gateway
    •	Distributed tracing
    Key Modules
    Problem	Spring Cloud Solution
    Config mgmt	Spring Cloud Config
    Discovery	Eureka / Consul
    Load balancing	Spring Cloud LoadBalancer
    Gateway	Spring Cloud Gateway
    Fault tolerance	Resilience4j
    Tracing	Sleuth / Micrometer
    Example
    spring.application.name=order-service
    spring.config.import=configserver:
    When to Use
    •	Microservices architecture
    •	Cloud / Kubernetes systems
    •	Distributed enterprise platforms

5.	How Boot works without XML in most cases?
    1️⃣ Spring Boot works without XML because it replaces XML-based configuration with annotation-driven Java configuration and auto-configuration, where beans are conditionally created based on the classpath, properties, and existing beans.
    ________________________________________
    1️⃣ What XML Used to Do (Before Boot)
    XML mainly did 4 things:
    1.	Define beans
    2.	Wire dependencies
    3.	Enable features (MVC, TX, AOP)
    4.	Configure infrastructure (DB, server, security)
    Spring Boot eliminates XML by automating all four.
    ________________________________________
    2️⃣ The Key Annotation: @SpringBootApplication
    @SpringBootApplication
    public class App {}
    This is actually three annotations:
    @Configuration
    @EnableAutoConfiguration
    @ComponentScan
    What Each Replaces from XML
    Annotation	Replaces XML
    @Configuration	<beans>
    @ComponentScan	<context:component-scan>
    @EnableAutoConfiguration	<mvc:annotation-driven>, <tx:annotation-driven>, etc.

    Do not use Spring Boot when its auto-configuration, runtime overhead, or opinionated model conflicts with your system’s constraints or simplicity requirements.
    ________________________________________
    1️⃣ When Application Is Very Small or Simple
    Example
    •	One-off utility
    •	Simple CLI tool
    •	Small batch script
    Why not Boot?
    •	Heavy dependency tree
    •	Slower startup
    •	Unnecessary abstractions
    ✅ Better alternatives:
    •	Plain Java
    •	Spring Core (minimal)
    •	Picocli
    ________________________________________
    2️⃣ Ultra-Low Latency or High-Performance Systems
    Examples
    •	High-frequency trading (HFT)
    •	Real-time analytics
    •	Game engines
    Why not Boot?
    •	Reflection
    •	Proxies
    •	GC pressure
    •	Larger memory footprint
    ✅ Better alternatives:
    •	Plain Java
    •	Netty
    •	Vert.x
    •	Go / Rust
    ________________________________________
    3️⃣ Serverless / Cold-Start Sensitive Environments
    Examples
    •	AWS Lambda
    •	Cloud Functions
    Why not Boot?
    •	Cold start latency (seconds vs milliseconds)
    •	Large JAR size
    ✅ Alternatives:
    •	Quarkus
    •	Micronaut
    •	Spring Boot + AOT (partial fix)
    ________________________________________
    4️⃣ You Need Full Control Over Every Component
    Examples
    •	Custom servlet containers
    •	Custom classloaders
    •	Non-standard threading models
    Why not Boot?
    •	Opinionated defaults
    •	Auto-configuration side effects

    •	Plain Spring Framework

    5️⃣ Legacy or Non-Standard Deployment Environments

    •	EAR deployments

    •	Embedded server conflicts
    •	Packaging constraints

    •	Traditional Spring (WAR/EAR)
    ________________________________________
    6️⃣ When Startup Time Is Critical
    Examples

    •	Context initialization overhead
    •	Classpath scanning
    Better:
    •	Lightweight frameworks
    •	Native images

2️⃣ Auto-Configuration (Most Important Section)
1.	What is auto-configuration?
    Auto-configuration in Spring Boot is a mechanism that automatically creates and configures Spring beans at application startup based on the classpath, application properties,
     and existing user-defined beans—so you don’t have to write explicit configuration.

2.	How does Spring Boot decide which auto-configuration class to load?
    Spring Boot loads all candidate auto-configuration classes from predefined metadata files and then decides which ones to apply by evaluating conditional annotations against the current classpath, environment properties, and existing beans.
    1️⃣ Step 1: Discover Auto-Configuration Classes
    Spring Boot does not guess auto-configs dynamically.
    It reads a fixed list at startup.
    Where the list comes from
    Spring Boot 3.x
    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
    Spring Boot ≤ 2.x
    META-INF/spring.factories
    These files contain entries like:
    org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
    org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration
    org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
    ➡ This is the universe of possible auto-configurations.
    ________________________________________
    2️⃣ Step 2: Register Auto-Configs as Candidates
    •	@EnableAutoConfiguration (via @SpringBootApplication)
    •	Imports all auto-config classes into the context
    •	They are treated like normal @Configuration classes
    ⚠️ At this stage, nothing is created yet.
    ________________________________________
    3️⃣ Step 3: Evaluate Conditional Annotations (Key Step)
    Each auto-configuration class is guarded by conditions.
    Example
    @Configuration
    @ConditionalOnClass(DataSource.class)
    @ConditionalOnMissingBean(DataSource.class)
    public class DataSourceAutoConfiguration {
    }
    Spring evaluates:
    a) Classpath conditions
    @ConditionalOnClass
    @ConditionalOnMissingClass
    ➡ “Is this library present?”
    ________________________________________
    b) Bean conditions
    @ConditionalOnBean
    @ConditionalOnMissingBean
    ➡ “Has the user already defined something?”
    ________________________________________
    c) Property conditions
    @ConditionalOnProperty
    ➡ “Is this feature enabled in config?”
    ________________________________________
    d) Environment conditions
    @ConditionalOnWebApplication
    @ConditionalOnNotWebApplication
    ➡ “What kind of app is this?”
    ________________________________________
    4️⃣ Step 4: Match or Skip Auto-Configuration
    If ALL conditions pass
    ✔ Auto-configuration is applied
    ✔ Beans inside it are registered
    If ANY condition fails
    ❌ Auto-configuration is skipped
    ❌ No beans created
    This decision is made during context refresh.
    ________________________________________
    5️⃣ Step 5: Ordering Matters
    Some auto-configs depend on others.
    Spring uses:
    @AutoConfigureBefore
    @AutoConfigureAfter
    @AutoConfigureOrder
    Example:
    @AutoConfigureAfter(DataSourceAutoConfiguration.class)
    public class HibernateJpaAutoConfiguration {}
    ➡ Ensures correct initialization order.
    ________________________________________
    6️⃣ Step 6: User Configuration Always Wins (Back-Off Rule)
    Most auto-configs use:
    @ConditionalOnMissingBean
    Meaning:
    “If the user defines this bean, don’t apply me.”
    This is how customization is preserved
    @ConditionalOnBean
    Apply this configuration ONLY IF a specific bean already exists in the Spring context.
    @ConditionalOnMissingBean
    Apply this configuration ONLY IF a specific bean does NOT exist in the Spring context.


3.	Role of @EnableAutoConfiguration.
    @EnableAutoConfiguration is a Spring Boot annotation that:
    •	Tells Spring Boot to automatically configure beans based on the classpath, environment, and defined beans.
    •	Reduces the need for manual configuration in XML or Java Config.
    •	Core idea: "Opinionated defaults with auto-configuration".
    It is usually used indirectly via:
    @SpringBootApplication
    Where:
    @SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan
    ________________________________________
    2️⃣ Purpose / Why It Exists
    Without auto-configuration:
    •	Developers had to manually declare beans for:
    o	DataSource
    o	EntityManager
    o	RestTemplate
    o	Thymeleaf, MVC, etc.
    •	Boilerplate code and complexity increased.
    With @EnableAutoConfiguration:
    •	Spring Boot detects dependencies (e.g., H2, Jackson, Thymeleaf) on the classpath.
    •	Automatically configures sensible defaults.
    •	Supports override: you can define your own beans, and Spring Boot will back off.
    ________________________________________
    3️⃣ How It Works Internally (Mechanics)
    1.	Meta-Annotation
    o	@EnableAutoConfiguration uses @Import(AutoConfigurationImportSelector.class)
    2.	AutoConfigurationImportSelector
    o	Reads /META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
    o	Finds all candidate auto-config classes
    o	Loads them conditionally using @Conditional* annotations
    3.	Conditional Loading
    Common conditions:
    o	@ConditionalOnClass → only configure if a class is on classpath
    o	@ConditionalOnBean → only configure if a bean exists
    o	@ConditionalOnMissingBean → only configure if bean is NOT present
    o	@ConditionalOnProperty → only configure if a property exists or has a value
    4.	Bean Registration
    o	Spring registers all conditional beans automatically
    o	If developer-defined bean exists, auto-configuration backs off
    ________________________________________
    4️⃣ Example
    @SpringBootApplication
    public class MyApp {
        public static void main(String[] args) {
            SpringApplication.run(MyApp.class, args);
         SpringApplication.run(MyApp.class, args);
        }
    }
    Auto-configures:
    Tomcat server (if spring-boot-starter-web)
    Jackson (if spring-boot-starter-json)
    HikariCP DataSource (if JDBC driver exists)
    Spring MVC or WebFlux defaults
    You can override by defining your own @Bean.

4.	What is spring.factories(Spring 2) vs (spring 3)AutoConfiguration.imports?
    META-INF/spring.factories
    Used by Spring Boot to list auto-configuration classes.

    Format:
    org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
    org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
    Mechanism:
    1.	@EnableAutoConfiguration imports AutoConfigurationImportSelector
    2.	It reads spring.factories
    3.	Loads all listed classes as candidate auto-configurations
    4.	Conditional beans (@ConditionalOnClass, @ConditionalOnMissingBean) are applied
    Limitations
    1.	Large classpath scanning
    o	Every library included meant spring.factories grows
    o	Startup overhead
    2.	No ordering guarantees
    o	Hard to manage auto-config precedence
    3.	Hard to modularize
    o	Each library contributes to same spring.factories file
    4.	Static / Immutable
    o	Adding or overriding auto-configuration required workarounds
    AutoConfiguration.imports
    •	File located at:
    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
    •	Replaces spring.factories for auto-configuration
    •	Contains plain list of auto-configuration classes:
    org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
    org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration
    Advantages
    1.	Faster startup
    o	Spring Boot uses build-time optimized loader
    o	No properties parsing, just class names
    2.	Supports grouping and ordering
    o	Can define AutoConfigurationGroup for load order
    3.	Better modularity
    o	Each module can declare its own auto-config imports without conflict
    4.	Future-proof
    o	Designed to support AOT / native image compilation (GraalVM, Spring Native)
    ________________________________________
    Mechanism (Spring Boot 3)
    1.	@EnableAutoConfiguration → imports AutoConfigurationImportSelector
    2.	Selector reads AutoConfiguration.imports files instead of spring.factories
    3.	Candidate classes are filtered using @Conditional*
    4.	Beans are registered


5.	How @ConditionalOnClass, @ConditionalOnBean work internally?
    •	Enable/disable bean registration based on environment, classpath, beans, properties, or resources.
    •	Core idea: Auto-configuration is conditional.
    Common ones:
    Annotation	Checks
    @ConditionalOnClass	Bean registered only if classes are on classpath
    @ConditionalOnMissingClass	Bean registered only if class not present
    @ConditionalOnBean	Bean registered only if another bean exists
    @ConditionalOnMissingBean	Bean registered only if bean does NOT exist
    @ConditionalOnProperty	Bean registered if a property exists or has a value
    @ConditionalOnResource	Bean registered if a resource exists

6.	How does Boot back off when user defines a bean?
    Spring Boot Auto-Configuration Back-Off:
    If a user provides their own bean of a certain type or name, Spring Boot will not register the auto-configured bean.
    •	Prevents bean conflicts
    •	Makes auto-configuration safe and overridable
    •	Works mainly via @ConditionalOnMissingBean and related annotations


7.	Order of auto-configuration loading.
    2️⃣ Ordering Mechanism
    Spring Boot provides several ways to influence order:
    ________________________________________
    (A) Using @AutoConfigureOrder
    •	@AutoConfigureOrder(int value) sets priority:
    @Configuration
    @AutoConfigureOrder(Ordered.HIGHEST_PRECEDENCE)
    public class MyAutoConfig { ... }
    •	Lower number → loaded earlier
    •	Higher number → loaded later
    •	Default: Ordered.LOWEST_PRECEDENCE if not specified
    ________________________________________
    (B) Using @AutoConfigureBefore / @AutoConfigureAfter
    •	Preferable over @AutoConfigureOrder for dependency-based ordering.
    @AutoConfigureBefore(DataSourceAutoConfiguration.class)
    public class MyCustomDataSourceAutoConfig { ... }

    @AutoConfigureAfter(WebMvcAutoConfiguration.class)
    public class MyPostMvcAutoConfig { ... }
    •	Spring Boot resolves dependencies between auto-config classes:
    o	before → run earlier
    o	after → run later
    •	Ensures beans are available when needed, e.g., DataSource must exist before JPA auto-config.
    ________________________________________
    (C) Natural Classpath Order
    •	If no order is specified:
    o	Classes are loaded in the order listed in AutoConfiguration.imports
    o	Alphabetical order in spring.factories used in older versions
    o	Still subject to @Conditional checks
    ________________________________________
    3️⃣ Execution Flow (Simplified)
    @EnableAutoConfiguration
              │
              ▼
     AutoConfigurationImportSelector
              │
              ▼
     Collect candidate auto-config classes
              │
              ▼
     Sort classes:
        ├─ @AutoConfigureOrder
        ├─ @AutoConfigureBefore / After
        └─ Default order
              │
              ▼
     Iterate classes:
      ┌───────────────────────┐
      │ Check @Conditional*   │
      │  - OnClass            │
      │  - OnBean             │
      │  - OnProperty         │
      └───────────────────────┘
              │
              ▼
     Register beans in context
    ________________________________________
    4️⃣ Important Notes
    1.	Conditional Annotations Are Always Respected
    o	Order only affects which auto-config classes are evaluated first, not whether they are skipped.
    2.	User-Defined Beans Take Precedence
    o	Even if an auto-config class runs early, @ConditionalOnMissingBean ensures back-off.
    3.	Custom Auto-Config in Libraries
    o	Always use @AutoConfigureBefore / @AutoConfigureAfter to avoid race conditions.
    4.	Spring Boot Starters
    o	Provide multiple auto-config classes, which may rely on ordering internally (e.g., Web → MVC → Jackson).
    5.	AOT / Native Image
    o	Auto-configuration ordering is precomputed to optimize startup

3.	What happens before and after ApplicationContext is created?
    1️⃣ Before ApplicationContext Creation
    Before the context is created, SpringApplication prepares the environment, listeners, and initializers:
    a) Prepare Environment
    •	Load configuration sources:
    o	application.properties / application.yml
    o	Command-line arguments
    o	Environment variables
    o	System properties
    •	Resolve active profiles and default profiles
    •	Build a ConfigurableEnvironment object
    b) Call ApplicationContextInitializers
    •	Custom initializers can manipulate the context before it is refreshed
    •	Example: adding property sources, configuring bean factories
    c) SpringApplicationRunListeners
    •	Internal hooks (SpringApplicationRunListeners) notify listeners:
    1.	starting() → app just started
    2.	environmentPrepared() → environment is ready but context not created
    •	Enables custom behavior at early startup
    d) Prepare for Context Type
    •	Decide the type of ApplicationContext to create:
    o	Web application: AnnotationConfigServletWebServerApplicationContext
    o	Non-web application: AnnotationConfigApplicationContext
    o	Reactive: AnnotationConfigReactiveWebApplicationContext
    •	Configure bean name generators and resource loaders
    ________________________________________
    2️⃣ ApplicationContext Creation
    •	Spring Boot creates the appropriate context instance
    •	Example: new AnnotationConfigServletWebServerApplicationContext()
    •	The context is empty initially, no beans instantiated yet
    •	The context is not yet refreshed (no singletons created, no beans injected)
    ________________________________________
    3️⃣ After ApplicationContext is Created
    Once the context object exists, Spring performs initialization and refresh:
    a) Apply Initializers
    •	ApplicationContextInitializers are called with the context instance
    •	You can register property sources, profiles, or modify the bean factory
    b) Register Listeners
    •	ApplicationListeners are registered
    •	Context can now publish events like:
    o	ApplicationPreparedEvent (context created but not refreshed)
    o	ApplicationStartedEvent (after context refresh)
    c) Refresh Context
    •	Instantiate singleton beans (component scan + auto-configuration)
    •	Dependency injection happens
    •	BeanPostProcessors applied
    •	@PostConstruct methods invoked
    •	AOP proxies (transactions, caching, security) are created
    d) Embedded Web Server Initialization (for web apps)
    •	DispatcherServlet and server start
    •	Servlet context initialized
    •	Application ready to accept requests
    e) Publish ApplicationReadyEvent
    •	Signals that Spring Boot app is fully started
    ________________________________________
    4️⃣ Summary Flow
    Before ApplicationContext:
      - Prepare environment & profiles
      - Notify SpringApplicationRunListeners (starting, environmentPrepared)
      - Decide context type
      - Call initializers

    Create ApplicationContext instance
      - Context exists, empty, not refreshed

    After ApplicationContext:
      - Apply initializers on context
      - Register listeners
      - Refresh context (instantiate beans, DI, post-processors)
      - Start embedded web server if applicable
      - Publish ApplicationStartedEvent / ApplicationReadyEvent


4.	Difference between ApplicationContextInitializer and ApplicationListener.
    1️⃣ Definitions
    Interface	Purpose
    ApplicationContextInitializer<C extends ConfigurableApplicationContext>	A callback interface used to customize or modify the ApplicationContext before it is refreshed.
    ApplicationListener<E extends ApplicationEvent>	A callback interface used to listen to events published by the ApplicationContext, either during startup or runtime.
    3️⃣ Typical Use Cases
    a) ApplicationContextInitializer
    public class MyInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {
        @Override
        public void initialize(ConfigurableApplicationContext context) {
            // add property source dynamically
            context.getEnvironment().getPropertySources()
                   .addFirst(new MapPropertySource("myProps", Map.of("foo", "bar")));
        }
    }
    •	Add profiles
    •	Add property sources
    •	Modify bean definitions programmatically before refresh
    b) ApplicationListener
    @Component
    public class MyListener implements ApplicationListener<ApplicationReadyEvent> {
        @Override
        public void onApplicationEvent(ApplicationReadyEvent event) {
            System.out.println("Application is ready!");
        }
    }
    •	React to lifecycle events:
    o	ApplicationStartingEvent
    o	ApplicationEnvironmentPreparedEvent
    o	ApplicationPreparedEvent
    o	ApplicationStartedEvent
    o	ApplicationReadyEvent
    •	React to custom events published via context.publishEvent()


5.	When are auto-configs applied in startup lifecycle?
    1️⃣ Context: What is Auto-Configuration?
    Spring Boot auto-configuration automatically configures beans and system settings based on classpath, environment, and user-defined beans, using annotations like @EnableAutoConfiguration and conditions like @ConditionalOnClass, @ConditionalOnMissingBean.
    •	Auto-configurations live in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.
    •	Triggered via @SpringBootApplication → @EnableAutoConfiguration.
    ________________________________________
    2️⃣ When Auto-Configurations Are Applied
    Auto-configurations are applied during ApplicationContext creation and refresh, specifically:
    Step 1: SpringApplication.run()
    1.	Prepare environment and profiles
    2.	Create ApplicationContext
    o	AnnotationConfigApplicationContext (non-web)
    o	AnnotationConfigServletWebServerApplicationContext (web)
    3.	Apply ApplicationContextInitializers
    4.	Load Bean Definitions
    ________________________________________
    Step 2: Component Scan + Auto-Configuration
    •	Spring Boot scans:
    o	Packages of your application (@ComponentScan)
    o	Auto-configuration classes (from spring.factories)
    •	@EnableAutoConfiguration imports classes conditionally
    •	Conditional annotations determine which beans are actually created:
    Conditional	Purpose
    @ConditionalOnClass	Only if a certain class exists in classpath
    @ConditionalOnBean	Only if another bean exists
    @ConditionalOnMissingBean	Only if a bean is missing
    @ConditionalOnProperty	Only if property is set
    @ConditionalOnWebApplication	Only for web apps
    •	Beans are registered in the BeanFactory but not instantiated yet.
    ________________________________________
    Step 3: Refresh ApplicationContext
    •	Context refresh triggers:
    1.	Bean instantiation (singleton beans created)
    2.	Dependency injection
    3.	Post-processing
    	BeanPostProcessors
    	AOP proxies (transactions, caching, security)
    4.	@PostConstruct methods
    •	At this point, auto-configured beans are fully initialized and injected as needed.
    ________________________________________
    3️⃣ Event Hooks
    Auto-configuration runs before ApplicationReadyEvent, but after:
    •	ApplicationEnvironmentPreparedEvent → environment is ready
    •	ApplicationPreparedEvent → context created but not refreshed
    ________________________________________
    4️⃣ Practical Example
    @SpringBootApplication
    public class MyApp {}
    •	@SpringBootApplication = @EnableAutoConfiguration + @ComponentScan + @Configuration
    •	Auto-config classes like DataSourceAutoConfiguration, WebMvcAutoConfiguration are loaded and registered as bean definitions
    •	Conditional logic checks:
    o	Is HikariCP on classpath?
    o	Is DataSource already defined?
    o	If conditions pass → beans created during context refresh
    ________________________________________
    5️⃣ Flow Summary
    SpringApplication.run()
       ↓
    Prepare environment & profiles
       ↓
    Create ApplicationContext
       ↓
    Call ApplicationContextInitializers
       ↓
    Component scan & register Auto-Configuration classes
       ↓
    Apply Conditional checks (@ConditionalOnClass, @ConditionalOnBean, etc.)
       ↓
    Refresh context → instantiate all beans (including auto-configured beans)
       ↓
    ApplicationReadyEvent published → app ready


6.	How embedded server (Tomcat/Jetty/Netty) is started?
    1️⃣ Detection of Web Application
    Spring Boot determines whether the application is web-enabled during SpringApplication.run():
    1.	Checks classpath:
    o	spring-webmvc → Servlet-based (Tomcat / Jetty / Undertow)
    o	spring-webflux → Reactive (Netty)
    2.	Sets WebApplicationType:
    o	SERVLET, REACTIVE, or NONE
    Spring Boot uses this info to decide which ApplicationContext to create:
    •	Servlet → AnnotationConfigServletWebServerApplicationContext
    •	Reactive → AnnotationConfigReactiveWebServerApplicationContext
    ________________________________________
    2️⃣ Auto-Configuration for Embedded Server
    •	Triggered via @EnableAutoConfiguration → spring-boot-autoconfigure → META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
    •	Servlet example:
    o	TomcatServletWebServerFactoryAutoConfiguration
    o	JettyServletWebServerFactoryAutoConfiguration
    o	UndertowServletWebServerFactoryAutoConfiguration
    •	Reactive example:
    o	NettyReactiveWebServerFactoryAutoConfiguration
    Conditional annotations ensure the correct server is used:
    @ConditionalOnClass({Tomcat.class})
    @ConditionalOnMissingBean(WebServerFactory.class)
    ________________________________________
    3️⃣ Bean Definition
    Spring Boot auto-configures:
    @Bean
    public TomcatServletWebServerFactory servletWebServerFactory() {
        return new TomcatServletWebServerFactory();
    }
    •	This is a factory bean for the embedded server
    •	Conditional checks prevent conflicts with user-defined servers
    ________________________________________
    4️⃣ Context Refresh & Server Initialization
    During context.refresh():
    1.	All singleton beans, including TomcatServletWebServerFactory, are instantiated
    2.	Spring Boot detects ServletWebServerFactory beans
    3.	Calls getWebServer():
    o	Creates an embedded Tomcat/Jetty/Undertow instance
    o	Configures:
    	Port (server.port)
    	Host (server.address)
    	Context path (server.servlet.context-path)
    	SSL settings
    	Session, connectors, etc.
    ________________________________________
    5️⃣ Start Server
    WebServer webServer = factory.getWebServer(new DispatcherServletRegistration());
    webServer.start();
    •	Embedded server starts listening on the configured port
    •	Servlet container initializes servlet context and servlets/filters (DispatcherServlet for MVC)
    •	Spring publishes:
    o	ServletWebServerInitializedEvent → allows beans to access the server
    ________________________________________
    6️⃣ Reactive Servers (Netty)
    •	For WebFlux apps:
    o	ReactiveWebServerFactory creates Netty server
    o	Binds routes and handlers instead of servlets
    o	Server starts asynchronously
    WebServer webServer = nettyFactory.getWebServer(routerFunctionAdapter);
    webServer.start();
    ________________________________________
    7️⃣ Spring Events During Server Startup
    Event	Timing
    ApplicationStartedEvent	After context refresh but before server starts
    ServletWebServerInitializedEvent	When embedded servlet container is initialized
    ApplicationReadyEvent	After server is running and app is ready to serve requests
    ________________________________________
    8️⃣ Summary Flow
    SpringApplication.run()
       ↓
    Determine WebApplicationType (Servlet / Reactive / None)
       ↓
    Create ApplicationContext (ServletWebServerApplicationContext / ReactiveWebServerApplicationContext)
       ↓
    Auto-configure WebServerFactory (Tomcat/Jetty/Netty)
       ↓
    Refresh context → instantiate beans
       ↓
    Call getWebServer() on WebServerFactory → create embedded server instance
       ↓
    Configure server (port, SSL, context path)
       ↓
    Start server → listen on port
       ↓
    Publish ServletWebServerInitializedEvent / ApplicationReadyEvent


7.	Application startup failure phases.
    1️⃣ Overview
    Spring Boot startup can fail at different phases, each with distinct causes:
    Phase	What happens	Typical Failures
    1. Bootstrap	main() → SpringApplication.run() → prepare environment	Missing or invalid JVM args, wrong main class, invalid spring.profiles.active
    2. Environment Preparation	Load properties (application.properties/yml), system env, command-line args	Property parsing errors, unresolved placeholders, invalid types
    3. ApplicationContext Creation	Create AnnotationConfigApplicationContext or ServletWebServerApplicationContext	Wrong context class, classpath missing, incompatible dependencies
    4. Initializer Execution	ApplicationContextInitializers run	Exceptions in initializers, custom property modifications failing
    5. Bean Definition Registration	Component scan + auto-configuration beans	ClassNotFound, BeanDefinitionParsingException, circular dependencies detected
    6. Bean Instantiation & Dependency Injection	Singleton beans created, DI applied	Unsatisfied dependencies, NoSuchBeanDefinition, circular references, @Autowired failures
    7. Bean Post-Processing	BeanPostProcessor, AOP proxies, @PostConstruct	Exceptions in @PostConstruct, AOP proxy creation failure
    8. Embedded Server Startup (Web apps)	Tomcat/Jetty/Netty starts	Port already in use, SSL misconfiguration, binding failure
    9. Application Runner / CommandLineRunner	Executed after context refresh	Runtime exceptions, business logic failures
    10. Event Publishing	ApplicationReadyEvent	Exceptions in listeners or async startup tasks
    ________________________________________
    2️⃣ Common Causes at Each Phase
    a) Environment Preparation
    •	Typo in application.properties: server.port=abc
    •	Missing required property
    •	Profile conflicts: activating non-existent profile
    b) Context Creation & Bean Registration
    •	Missing dependency: Spring cannot find class on classpath
    •	Circular dependency between beans
    •	Auto-configuration fails due to missing class (@ConditionalOnClass fails)
    c) Bean Instantiation
    •	@Autowired target bean missing
    •	Constructor injection exception
    •	@Value fails because property is not resolvable
    d) Embedded Server Startup
    •	Port in use: Tomcat started on port 8080 (port already in use)
    •	SSL misconfiguration: invalid keystore
    •	Reactive server Netty binding failure
    e) Application Runner Execution
    •	Exceptions in run() methods of CommandLineRunner / ApplicationRunner
    •	Business logic failure causing startup abort
    ________________________________________
    3️⃣ How Spring Boot Reports Failures
    •	Startup logs show phase-specific messages
    •	SpringApplicationRunListeners publish:
    o	ApplicationFailedEvent
    •	Exception stack traces include:
    o	Root cause (e.g., BeanCreationException, PortInUseException)
    o	Suppressed exceptions (e.g., circular dependencies)
    •	Boot also provides “caused by” hints for easier debugging
    ________________________________________
    4️⃣ Lifecycle Events for Failure
    Spring Boot fires events even on failure:
    1.	ApplicationStartingEvent → app just started
    2.	ApplicationEnvironmentPreparedEvent → environment ready
    3.	ApplicationPreparedEvent → context created
    4.	Failure → ApplicationFailedEvent
    o	Provides throwable causing startup failure
    o	Can be used for custom logging or alerting
    ________________________________________

    main() -> SpringApplication.run()
       ↓
    Prepare Environment -> failure? -> ApplicationFailedEvent
       ↓
    Create ApplicationContext -> failure? -> ApplicationFailedEvent
       ↓
    Apply Initializers -> failure? -> ApplicationFailedEvent
       ↓
    Register Bean Definitions -> failure? -> ApplicationFailedEvent
       ↓

       ↓

       ↓
    Start Embedded Server -> failure? -> ApplicationFailedEvent
       ↓
    ApplicationRunner / CommandLineRunner -> failure? -> ApplicationFailedEvent
       ↓
    ApplicationReadyEvent


8.	How Boot supports reactive and servlet stacks differently?
    1️⃣ Web Stack Detection
    Spring Boot detects the type of application during startup:
    SpringApplication application = new SpringApplication(MyApp.class);
    application.setWebApplicationType(WebApplicationType.SERVLET / REACTIVE / NONE);
    •	SERVLET: spring-webmvc on classpath → traditional blocking stack (Tomcat, Jetty, Undertow)
    •	REACTIVE: spring-webflux on classpath → reactive, non-blocking stack (Netty or Undertow reactive)
    •	NONE: CLI apps or batch jobs
    Detection happens before ApplicationContext creation and affects which context is instantiated.


9.	What is SpringApplicationRunListener?
    SpringApplicationRunListener is an interface that allows you to hook into the lifecycle of a Spring Boot application.
    It is used internally by Spring Boot to trigger events at specific phases of startup, and you can implement it for custom behavior.
    •	Implemented internally by Spring Boot for logging, metrics, failure handling, etc.
    •	Hook points occur before, during, and after ApplicationContext creation.
    •	2️⃣ Key Methods in the Interface
    Method	When Called
    starting()	Immediately when SpringApplication.run() is invoked, before environment is prepared
    environmentPrepared(ConfigurableEnvironment environment)	After environment is prepared but before context creation
    contextPrepared(ConfigurableApplicationContext context)	After context instance is created but before bean definitions are loaded
    contextLoaded(ConfigurableApplicationContext context)	After bean definitions are loaded but before context refresh
    started(ConfigurableApplicationContext context)	After context refresh, before web server starts
    running(ConfigurableApplicationContext context)	After context refresh and web server is started, app is running
    failed(ConfigurableApplicationContext context, Throwable exception)	If any exception occurs during startup, triggered with root cause
    Simplified Spring Boot startup with RunListener hooks:
    SpringApplication.run()
       ↓
    RunListeners.starting() → ApplicationStartingEvent
       ↓
    Prepare Environment
    RunListeners.environmentPrepared() → ApplicationEnvironmentPreparedEvent
       ↓
    Create ApplicationContext
    RunListeners.contextPrepared() → ApplicationPreparedEvent
       ↓
    Load Bean Definitions
    RunListeners.contextLoaded() → ApplicationPreparedEvent (again for loaded beans)
       ↓
    Refresh Context → Beans instantiated
    RunListeners.started() → ApplicationStartedEvent
       ↓
    Start embedded web server
    RunListeners.running() → ApplicationReadyEvent
       ↓
    Failure? → RunListeners.failed() → ApplicationFailedEvent
    •	Provides early and late hooks in the lifecycle
    •	Used by Spring Boot internally for event publishing, logging, and diagnostics

    5️⃣ Use Cases for Custom RunListeners
    1.	Custom logging during startup (before any beans exist)
    2.	Environment manipulation before ApplicationContext creation
    3.	Custom metrics / monitoring
    4.	Failure handling / alerting before Spring shuts down


10.	How startup time can be reduced?
    1️⃣ Use Lazy Initialization
    •	By default, Spring Boot eagerly creates all singleton beans at startup.
    •	Enable lazy initialization to defer bean creation until needed:
    @SpringBootApplication
    @EnableLazyInitialization
    public class MyApp {}
    •	Or per-bean:
    @Bean
    @Lazy
    public MyService myService() { ... }
    Effect: Fewer beans are instantiated at startup → faster startup.
    ________________________________________
    2️⃣ Exclude Unused Auto-Configurations
    •	Spring Boot auto-configures many features by default. Some may be unused.
    •	Exclude unnecessary auto-configs:
    @SpringBootApplication(exclude = {
        DataSourceAutoConfiguration.class,
        JmxAutoConfiguration.class
    })
    •	Use --debug to see the auto-configuration report and disable irrelevant ones.
    ________________________________________
    3️⃣ Use Spring Boot 3 Features
    •	Native image compilation (GraalVM) can dramatically reduce startup.
    •	Use spring-native / AOT compilation to precompute bean definitions.
    ________________________________________
    4️⃣ Reduce Classpath Scanning
    •	Limit @ComponentScan to necessary packages:
    @ComponentScan(basePackages = "com.example.myapp")
    •	Avoid scanning the entire com.example package if not needed.
    ________________________________________
    5️⃣ Use Lazy Web Server Startup
    •	Delay embedded server initialization until first request:
    server.lazy-initialization=true
    •	Reduces startup time for services that may not immediately handle requests.
    ________________________________________
    6️⃣ Avoid Heavy Initializers & CommandLineRunner
    •	Beans like CommandLineRunner or heavy @PostConstruct logic slow startup.
    •	Move heavy tasks to async threads or execute after ApplicationReadyEvent.
    ________________________________________
    7️⃣ Optimize Logging
    •	Reduce logging overhead:
    o	Disable debug/trace in production
    o	Use asynchronous logging (AsyncAppender) if many logs occur at startup
    ________________________________________
    8️⃣ Use Native Image / AOT Compilation
    •	Spring Boot 3 + GraalVM Native or Spring AOT:
    o	Pre-computes bean definitions
    o	Reduces reflection usage
    o	Can reduce startup time from seconds → milliseconds
    ________________________________________
    9️⃣ Profile-Based Conditional Beans
    •	Use profiles to load only necessary beans in dev vs prod:
    @Profile("prod")
    @Bean
    public HeavyService heavyService() { ... }
    •	Prevents unnecessary beans in certain environments.
    ________________________________________
    🔟 Avoid Circular Dependencies
    •	Circular dependencies cause Spring to resolve proxies → slower startup
    •	Refactor beans to remove cycles
    ________________________________________
    11️⃣ Use Light Context for Tests
    •	For integration tests, use:
    @SpringBootTest(classes = MyTestConfig.class)
    •	Avoid loading the full context unnecessarily.

    ➡️ Problem: Spring felt heavy compared to newer frameworks.
    ________________________________________
    2️⃣ Why Spring Boot was created (the real reason)
    👉 Spring Boot was created to remove friction, not replace Spring.
    Spring Boot = Spring Framework + Opinionated Defaults + Production Readiness


    ✅ Advantages of Spring Boot
    1. Rapid Development (Auto-configuration)
    •	Spring Boot auto-configures beans based on classpath and properties.
    •	Reduces boilerplate XML and Java config.
    •	Example: DataSource, JPA, Jackson, Tomcat auto-setup.
    Why it matters:
    ➡ Faster time-to-market, fewer configuration errors.
    ________________________________________
    2. Embedded Servers
    •	Comes with embedded Tomcat / Jetty / Undertow.
    •	No need to deploy WAR files to external app servers.
    Benefit:
    •	Easy containerization (Docker).
    •	Consistent behavior across environments.
    ________________________________________
    3. Opinionated Defaults (Convention over Configuration)
    •	Sensible defaults for logging, security, JSON, metrics.
    •	You can override when needed.
    Real-world impact:
    •	Teams follow consistent standards.
    •	New developers onboard faster.
    ________________________________________
    4. Production-Ready Features (Actuator)
    •	Health checks, metrics, readiness/liveness probes.
    •	Integration with Prometheus, Grafana, Kubernetes.
    Critical for microservices:
    •	Observability, monitoring, autoscaling.
    ________________________________________
    5. Strong Microservices Ecosystem
    •	Seamless integration with:
    o	Spring Cloud (Config, Gateway, Circuit Breakers)
    o	Kafka, Redis, NoSQL
    o	REST, gRPC, WebFlux
    Why seniors like it:
    ➡ Solves cross-cutting concerns out of the box.
    ________________________________________
    6. Easy Externalized Configuration
    •	application.yml, profiles (dev, test, prod)
    •	Environment variables & config servers.
    Key for cloud-native apps
    ________________________________________
    7. Large Community & Enterprise Support
    •	Huge ecosystem, frequent updates.
    •	Backed by VMware / Broadcom.
    ________________________________________

    ❌ Disadvantages of Spring Boot
    1. Hidden Complexity
    •	Auto-configuration can feel like a black box.
    •	Debugging startup issues requires deep Spring knowledge.
    Senior-level pain point:
    •	“Why is this bean getting created?”
    ________________________________________
    2. Startup Time & Memory Overhead
    •	Slower startup compared to:
    o	Quarkus
    o	Micronaut
    o	Node.js / Go
    Impact:
    •	Cold starts in serverless or Kubernetes scaling.
    (Though Spring Native / AOT helps)
    ________________________________________
    3. Overkill for Simple Applications
    •	For small services or scripts, Spring Boot can be heavy.
    •	More dependencies than necessary.
    ________________________________________
    4. Less Control Over Configuration
    •	Opinionated defaults sometimes fight custom needs.
    •	Requires exclusions or manual overrides.
    Example:
    @SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
    ________________________________________
    5. Version Compatibility Challenges
    •	Dependency versions managed by Spring BOM.
    •	Upgrading Boot can break:
    o	Spring Cloud
    o	Hibernate
    o	Third-party starters
    ________________________________________
    6. Not Ideal for Ultra-Low Latency Systems
    •	Reflection, proxies, GC overhead.
    •	Not preferred for:
    o	HFT systems
    o	Real-time systems
    ________________________________________
    7. Learning Curve for Internals
    •	To use it well, you must understand:
    o	Bean lifecycle
    o	AutoConfiguration
    o	Conditional annotations
    o	AOP & proxies

1️⃣ Entry Point: main Method
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
•	SpringApplication.run() is the starting point
•	Internally, it calls new SpringApplication(...) and then run(args)
________________________________________
2️⃣ SpringApplication.run()
Main responsibilities:
1.	Create SpringApplication instance
2.	Prepare environment
o	Read application.properties / application.yml
o	Profiles and command-line arguments
3.	Create ApplicationContext
o	Usually AnnotationConfigApplicationContext (non-web)
o	Or AnnotationConfigServletWebServerApplicationContext (web)
4.	Register ApplicationContextInitializers and ApplicationListeners
5.	Load ApplicationContext and refresh beans
6.	Trigger ApplicationStartedEvent, ApplicationReadyEvent
________________________________________
3️⃣ Environment Preparation
•	Spring Boot reads:
o	application.properties / application.yml
o	Environment variables
o	Command-line arguments
•	Configures Environment object
•	Activates profiles (@Profile)
________________________________________
4️⃣ Bean Definition & Classpath Scanning
1.	@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan
2.	Component scanning:
o	Scans packages for @Component, @Service, @Repository, @Controller
o	Registers bean definitions in BeanFactory
3.	Auto-configuration:
o	Spring Boot loads classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
o	Conditional annotations (@ConditionalOnClass, @ConditionalOnBean) determine which auto-config beans are created
4.	BeanPostProcessors are registered for lifecycle callbacks (e.g., @PostConstruct)
________________________________________
5️⃣ ApplicationContext Refresh
context.refresh() triggers Spring lifecycle:
1.	Instantiate singleton beans:
o	Constructor injection → dependencies injected
o	Field/setter injection → applied
2.	BeanPostProcessor execution
o	@PostConstruct methods executed
3.	SmartInitializingSingleton
o	For beans that require all other singletons to be ready
4.	Event publishing
o	ApplicationContextInitializedEvent
o	ApplicationStartedEvent
________________________________________
6️⃣ Embedded Web Server Initialization (if Web App)
•	Spring Boot detects web environment → starts Tomcat / Jetty / Undertow
•	Creates ServletWebServerApplicationContext
•	Registers DispatcherServlet (@Controller endpoints)
•	Servlet context initialized
•	HTTP server starts listening on configured port (default 8080)
________________________________________
7️⃣ Application Ready Event
•	After context.refresh() and web server startup, Spring publishes:
o	ApplicationReadyEvent
•	Indicates app is fully started and ready to serve requests
________________________________________
8️⃣ Lifecycle Hooks / Extension Points
Hook	Triggered by
ApplicationContextInitializer	Before context is refreshed
ApplicationRunner / CommandLineRunner	After context refresh, just before ready
@PostConstruct	After bean instantiation, before ready
SmartInitializingSingleton	After all singleton beans are instantiated
ApplicationStartedEvent / ApplicationReadyEvent	Event listeners can hook in
________________________________________
