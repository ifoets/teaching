5.	How does Spring resolve dependencies internally?
    1️⃣ Overview
    •	Spring resolves dependencies via Dependency Injection (DI).
    •	It supports:
    o	Constructor injection
    o	Setter injection
    o	Field injection (@Autowired)
    •	Dependencies can be:
    o	Singleton or prototype beans
    o	Optional or required
    •	Resolution happens inside the BeanFactory / ApplicationContext using BeanDefinition metadata.
    ________________________________________
    2️⃣ Internal Resolution Flow
    Step 1: BeanDefinition Lookup
    •	When a bean is created:
    1.	Spring retrieves its BeanDefinition from the container
    2.	Checks the scope (singleton, prototype, etc.)
    3.	Reads constructor args, property values, autowire metadata
    ________________________________________
    Step 2: Identify Dependencies
    •	Spring scans for dependencies:
    o	Constructor parameters
    o	Setter methods
    o	Fields annotated with @Autowired
    •	Marks them for injection.
    ________________________________________
    Step 3: Dependency Resolution
    •	By Type:
    o	Finds candidate beans of the required type
    o	Uses primary/qualifier annotations if multiple candidates exist
    •	By Name:
    o	Matches bean name with parameter/field name
    •	Collections / Arrays:
    o	Injects all matching beans as list/map
    •	Optional / Lazy:
    o	Can inject Optional<T> or ObjectProvider<T> to delay resolution
    ________________________________________
    Step 4: Circular Dependency Handling
    •	Spring can resolve circular dependencies for singleton beans:
    o	Phase 1: Instantiate bean (constructor)
    o	Phase 2: Populate properties (setter/field injection)
    o	Phase 3: Apply BeanPostProcessors and initialize
    •	Circular dependencies constructor-based → fails, because object not created yet
    ________________________________________
    Step 5: Bean Creation & Injection
    •	Instantiate bean using:
    o	Default constructor
    o	Autowired constructor
    •	Inject dependencies:
    o	Setter injection
    o	Field injection
    •	Apply BeanPostProcessors:
    o	e.g., @Transactional, AOP proxies
    •	Call lifecycle callbacks:
    o	@PostConstruct, afterPropertiesSet()

7.	Constructor injection vs setter injection – when and why?
    1️⃣ Constructor Injection
    Definition
    •	Dependencies are provided via the constructor at bean creation.
    •	Promotes immutability (final fields).
    Example:
    @Component
    public class Service {
        private final Repository repo;

        @Autowired
        public Service(Repository repo) {
            this.repo = repo; // injected at creation
        }
    }
    ✅ Pros
    1.	Mandatory dependencies enforced → bean cannot be created without them
    2.	Immutability → fields can be final
    3.	Thread-safe by default
    4.	Better for unit testing → all dependencies required upfront
    5.	Encourages clean design / constructor-based programming
    ❌ Cons
    •	Can become verbose if many dependencies exist
    •	Not ideal for optional dependencies (requires overloads or @Autowired(required=false))

        @Autowired(required=false)

        •	By default, required=true
        •	Spring must find exactly one bean of type SomeService
        •	If no bean is found → NoSuchBeanDefinitionException
        •	If multiple beans are found → NoUniqueBeanDefinitionException
        ________________________________________
        2️⃣ required=false Behavior
        @Autowired(required=false)
        private SomeService service;
        What it does:
        1.	Spring will inject the bean if present
        2.	If no bean is found, it will inject null
        3.	No exception is thrown


    ________________________________________
    2️⃣ Setter Injection
    Definition
    •	Dependencies are provided via setter methods after bean instantiation.
    •	Fields are usually non-final.
    Example:
    @Component
    public class Service {
        private Repository repo;

        @Autowired
        public void setRepo(Repository repo) {
            this.repo = repo; // injected after creation
        }
    }
    ✅ Pros
    1.	Optional dependencies supported easily (required=false)
    2.	Flexible → allows circular dependencies (singleton setter injection)
    3.	Reduces constructor verbosity for beans with many optional dependencies
    ❌ Cons
    •	Dependencies can be mutated after creation
    •	Bean may be in partially initialized state
    •	Less ideal for immutable / thread-safe design

8.	How does Spring handle circular dependencies?
//If two beans depend on each other via constructor injection, Spring throws:
    1 Constructor Injection
    •	Spring cannot resolve circular dependencies with constructor injection.
    •	Reason: Constructor injection requires the complete instance upfront.
    •	Result: BeanCurrentlyInCreationException
    Setter / Field Injection
    •	Spring can resolve circular dependencies via three-level caching:
    1.	SingletonObjects → fully initialized beans
    2.	EarlySingletonObjects → partially initialized beans (early reference)
    3.	SingletonFactories → ObjectFactory to create bean proxies
    How it works
    1.	Spring detects A is being created.
    2.	Creates a partial instance of A (without dependencies fully injected) and adds it to earlySingletonObjects.
    3.	When creating B, Spring sees A is in earlySingletonObjects → injects the early reference.
    4.	Spring finishes property injection for both beans.
    3. Important Notes
    3.1 Prototype Beans
    •	Spring cannot resolve circular dependencies for prototype-scoped beans, even with setter injection.
    •	Reason: Prototype beans are created fresh each time and aren’t cached.
    3.2 Lazy Initialization
    •	Using @Lazy can break circular dependency for constructor injection:
    @Component
    class A {
        private final B b;
        public A(@Lazy B b) { this.b = b; }
    }
    .3 @PostConstruct Timing
    •	Circular references can affect initialization order.
    •	PostConstruct methods are invoked after all dependencies are injected.
    4. Best Practices
    1.	Avoid circular dependencies — usually indicates design smell.
    2.	If unavoidable:
    o	Use setter/field injection for circular beans.
    o	Consider @Lazy injection.
    5. Spring’s Internal Handling (Advanced)
    •	SingletonFactory → produces proxy / early reference
    •	DefaultSingletonBeanRegistry maintains:
    1.	singletonObjects (fully initialized)
    2.	earlySingletonObjects (partial)
    3.	singletonFactories (proxies)
    •	Circular dependency is detected in createBean() → populateBean() phase.

    Overview

3.	When exactly is @PostConstruct called?
    @PostConstruct is called after the bean is fully instantiated and all dependencies are injected,
    but before the bean is made available for use and before any BeanPostProcessor.postProcessAfterInitialization() logic (like AOP proxies) is applied.
4.	What happens if BeanPostProcessor throws exception?
    f a BeanPostProcessor throws an exception, Spring fails the creation of that bean,
    stops context initialization (for singletons), and the application startup fails with a BeanCreationException.

5.	How does @PreDestroy work?
    @PreDestroy is called by the Spring container during bean destruction, after the ApplicationContext is closed, allowing the bean to release resources. It is executed only for container-managed beans, mainly singletons, before the JVM shuts down.

6.	How does Spring destroy prototype beans?
    Spring does NOT manage the full lifecycle of prototype beans. It creates them, injects dependencies, and then hands them over to the client. Destruction callbacks (@PreDestroy, destroy-method) are NOT automatically called for prototype beans.
    Why Spring behaves this way (Design Reason)
    •	Prototype scope = new instance per request
    •	Container cannot track:
    o	Who is using the instance
    o	When it is safe to destroy it
    •	Therefore, Spring intentionally stops lifecycle management after creation
    What Spring DOES for prototype beans
    ✔ Instantiates the bean
    ✔ Performs dependency injection
    ✔ Calls @PostConstruct
    ✔ Applies BeanPostProcessors
    🚫 Does NOT:
    •	Call @PreDestroy
    •	Call DisposableBean.destroy()
    •	Invoke custom destroy methods

    getBean()
       ↓
    Constructor
       ↓
    Dependency Injection
       ↓
    @PostConstruct
       ↓
    Bean returned to caller
       ↓
    ❌ Spring lifecycle ends here

    You must handle destruction yourself.
    MyPrototypeBean bean = context.getBean(MyPrototypeBean.class);
    bean.destroy(); // manual call

3️⃣ Spring AOP (Most Failed Area)
1.	What problem does Spring AOP solve?
    Spring AOP solves the problem of cross-cutting concerns—logic that is needed across many parts of an application but does not belong to core business logic.
    The core problem: Cross-cutting concerns
    These are concerns that:
    •	Appear in many classes
    •	Are orthogonal to business logic
    •	Cause code duplication and tight coupling
    Common examples
    •	Logging
    •	Transaction management
    •	Security / authorization
    •	Metrics
    •	Caching
    •	Tracing
    •	Retry logic
    What Spring AOP actually does
    Spring AOP:
    •	Intercepts method calls
    •	Applies logic based on:
    o	Annotations
    o	Pointcuts
    Uses proxies (JDK or CGLIB)
2.	Difference between JDK proxy vs CGLIB proxy.
    JDK proxies work by implementing interfaces, while CGLIB proxies work by subclassing concrete classes.
    Spring chooses JDK proxies when an interface is present; otherwise it falls back to CGLIB.

    •	Aspect	•	JDK Dynamic Proxy	•	CGLIB Proxy
    •	Proxy type	•	Interface-based	•	Class-based
    •	Requires interface	•	✅ Yes	•	❌ No
    •	Mechanism	•	java.lang.reflect.Proxy	•	Bytecode generation
    •	Inheritance	•	Implements interface	•	Extends target class
    •	Final classes	•	❌ Not allowed	•	❌ Not allowed
    •	Final methods	•	✅ Allowed	•	❌ Not intercepted
    •	Performance	•	Slightly slower	•	Slightly faster
    •	Memory	•	Lower	•	Higher
    •	Default in Spring	•	Yes (if interface exists)	•	Fallback

4.	Why self-invocation breaks AOP?
    Spring AOP is proxy-based. Self-invocation calls a method directly on the target object (this), bypassing the proxy, so AOP advice is never applied.
    1️⃣ How Spring AOP actually works
    Spring does not modify your class directly.
    It creates a proxy around your bean.
    Client → Proxy → Target Bean
    •	Advice (@Transactional, @Cacheable, etc.) runs in the proxy
    •	Only method calls that go through the proxy are intercepted
    ________________________________________
    2️⃣ The self-invocation problem
    @Service
    public class OrderService {

        @Transactional
        public void createOrder() {
            updateInventory();   // ❌ self-invocation
        }

        @Transactional
        public void updateInventory() {
            // DB update
        }
    }
    What happens at runtime
    Client → Proxy → createOrder()
                        ↓
                    this.updateInventory()  ❌
    •	updateInventory() is called on this
    •	The proxy is skipped
    •	No transaction advice is applied
    How to fix self-invocation (important)
    ✅ Option 1: Move method to another bean (BEST)
    @Service
    public class InventoryService {

        @Transactional
        public void updateInventory() {}
    }
    @Service
    public class OrderService {

        private final InventoryService inventoryService;

        public void createOrder() {
            inventoryService.updateInventory(); // ✔ via proxy
        }
    }


5.	How does Spring create proxy internally?
    Spring creates proxies using either JDK dynamic proxies or CGLIB during bean creation, based on whether the bean implements an interface. These proxies intercept method calls and apply AOP advice via an interceptor chain.
    Big picture flow
    Bean Definition
       ↓
    Bean Instantiation
       ↓
    BeanPostProcessors
       ↓
    AbstractAutoProxyCreator
       ↓
    Proxy created (JDK or CGLIB)
       ↓
    Proxy replaces original bean in context

6.	What is a Join Point, Pointcut, Advice?
    A join point is a specific point in the program execution where an aspect can be applied.
    In Spring AOP
    •	Only method execution join points are supported
    A join point represents a well-defined point during program execution, such as a method invocation.
    A pointcut is a predicate (expression) that selects which join points should be intercepted./ Which methods should this aspect apply to?
    A pointcut defines a set of join points where advice should be applied.
    @Before	Before method execution
    @After	After method (finally)
    @AfterReturning	After successful return
    @AfterThrowing	On exception
    @Around	Before & after (full control)

7.	Difference between @Around vs @Before vs @AfterReturning.
    @Around has full control over method execution, while @Before runs only before the method and @AfterReturning runs only after successful completion.
8.	Can final methods be proxied? Why not?
    Final methods cannot be proxied by Spring AOP when using CGLIB, because CGLIB works by creating a subclass and overriding methods—and final methods cannot be overridden.
9.	Order of multiple aspects.
    When multiple aspects apply to the same join point, Spring needs a defined execution order.
            @Aspect
            @Component
            public class LoggingAspect {
                @Before("execution(* service.*.*(..))")
                public void log() { System.out.println("Logging"); }
            }

            @Aspect
            @Component
            public class SecurityAspect {
                @Before("execution(* service.*.*(..))")
                public void check() { System.out.println("Security Check"); }
            }
            Which @Before runs first?

            By default: undefined, depends on Spring internal proxy ordering.
            Controlling order with @Order
            Spring provides the @Order annotation:
            @Aspect
            @Component
            @Order(1)
            public class SecurityAspect { }

            @Aspect
            @Component
            @Order(2)
            public class LoggingAspect { }

4️⃣ Spring Transaction Management (Critical)
1.	What happens internally when @Transactional is used?
    @Transactional tells Spring: “Execute this code within a transaction context, commit if successful, roll back if an exception occurs.”
    But Spring does not modify your code directly. It uses proxies.
    1️⃣ Core Idea
    @Transactional tells Spring: “Execute this code within a transaction context, commit if successful, roll back if an exception occurs.”
    But Spring does not modify your code directly. It uses proxies.
    ________________________________________
    2️⃣ Spring’s Transaction Mechanism
    Step 1: Proxy Creation
    •	At runtime, Spring wraps the target bean in a proxy (JDK dynamic proxy or CGLIB)
    o	JDK proxy → if bean implements interface
    o	CGLIB → if no interface or explicitly configured
    •	The proxy intercepts calls to methods annotated with @Transactional.
    ________________________________________
    Step 2: Method Interception
    •	Proxy intercepts method call → invokes TransactionInterceptor
    •	TransactionInterceptor delegates to PlatformTransactionManager
    •	Determines:
    o	Existing transaction? (Propagation rules)
    o	Isolation level
    o	Read-only flag
    o	Timeout
    ________________________________________
    Step 3: Transaction Lifecycle
    a) Begin Transaction
    tx = transactionManager.getTransaction(definition)
    •	Binds transaction to current thread
    •	Uses TransactionSynchronizationManager internally
    b) Execute Method
    •	Target method executes
    •	Any DB operations participate in this transaction
    •	Spring does not touch JDBC/ORM code directly — it relies on the transaction manager
    c) Commit / Rollback
    •	On successful completion:
    transactionManager.commit(tx)
    •	On runtime exception (unchecked):
    transactionManager.rollback(tx)
    •	Checked exceptions → do not trigger rollback by default, unless configured


2.	PlatformTransactionManager role.
    1️⃣ Core Role
    PlatformTransactionManager is responsible for creating, committing, and rolling back transactions in Spring, regardless of whether the underlying technology is JDBC, JPA, Hibernate, JMS, or JTA.
    It decouples your code from specific transaction implementations.
    ________________________________________
    2️⃣ Key Methods
    TransactionStatus getTransaction(TransactionDefinition definition);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
    ________________________________________
    a) getTransaction()
    •	Called before your @Transactional method executes
    •	Responsibilities:
    o	Check for existing transaction (propagation rules)
    o	If necessary, start a new transaction
    o	Bind resources (DB connection, Hibernate session) to the current thread
    •	Returns TransactionStatus representing the current transaction
    ________________________________________
    b) commit()
    •	Called after successful method execution
    •	Responsibilities:
    o	Commit the underlying transaction
    o	Unbind resources from the thread
    o	Trigger any synchronizations registered (TransactionSynchronizationManager)
    ________________________________________
    c) rollback()
    •	Called if an exception occurs
    •	Responsibilities:
    o	Roll back the underlying transaction
    o	Unbind resources from the thread
    o	Notify synchronizations of rollback
    ________________________________________
    3️⃣ How It Works With @Transactional
    1.	Proxy intercepts method call → calls TransactionInterceptor
    2.	TransactionInterceptor calls PTM.getTransaction()
    3.	PTM starts / joins a transaction
    4.	Method executes
    5.	PTM.commit() or rollback() based on outcome


3.	Difference between local vs global transactions.
    Term	Meaning
    Local Transaction	A transaction that involves a single resource (e.g., one database). Managed by the resource’s native transaction manager.
    Global Transaction (Distributed Transaction / XA Transaction)	A transaction that spans multiple resources (e.g., two databases, or DB + JMS). Managed by a transaction coordinator using a protocol like XA / 2PC.
    ________________________________________
    2️⃣ Key Differences
    Feature	Local Transaction	Global Transaction
    Scope	Single resource	Multiple resources
    Manager	Resource-specific (JDBC, Hibernate)	Distributed coordinator (JTA)
    Protocol	Native commit/rollback	Two-Phase Commit (2PC)
    Performance	Fast, minimal overhead	Slower due to coordination
    Complexity	Simple	Complex, failure handling needed
    Example	DataSourceTransactionManager for one DB	JtaTransactionManager coordinating multiple DBs or JMS
    ________________________________________
    3️⃣ How Local Transaction Works
    1.	Start transaction
    2.	Perform operations on a single database
    3.	Commit / rollback
    4.	Managed entirely by the DB
    ✅ Low latency, simple, no distributed protocol needed
    ________________________________________
    4️⃣ How Global Transaction Works
    1.	Start transaction via transaction coordinator
    2.	Operations on multiple resources (DB1, DB2, JMS, etc.)
    3.	Phase 1: Prepare
    o	Each resource tells coordinator “I’m ready to commit”
    4.	Phase 2: Commit / Rollback
    o	Coordinator instructs all resources to commit or rollback
    5.	Failure handling: if one resource fails → rollback all
    ⚠️ Slower due to 2PC, but ensures ACID across multiple resources
    ________________________________________
    5️⃣ Spring Context
    •	Local: Use DataSourceTransactionManager for JDBC
    •	Global: Use JtaTransactionManager for XA transactions (multiple DBs or messaging systems)
    •	@Transactional will work with both, depending on configured transaction manager
    ________________________________________
    6️⃣ When to Use Which
    Scenario	Recommended
    Single database / single JMS queue	Local
    Multiple DBs, multiple JMS queues, microservices requiring ACID	Global (XA / 2PC)
    Microservices using eventual consistency	Prefer saga / compensation pattern instead of global transactions


4.	Transaction propagation types with real use cases.
    a) REQUIRED (Most Common)
    @Transactional
    public void createUser() {
        saveUserToDB();
        auditService.logUserCreation(); // REQUIRED by default joins same transaction
    }
    •	If saveUserToDB() fails → entire transaction rolls back, including audit
    ________________________________________
    b) REQUIRES_NEW
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAudit() {
        saveAuditToDB();
    }
    •	Suspends parent transaction
    •	Commits independently
    •	Useful when audit must persist even if parent fails
    ________________________________________
    c) NESTED
    @Transactional(propagation = Propagation.NESTED)
    public void calculateDiscount() {
        if(error) throw new RuntimeException();
    }
    •	Creates savepoint inside parent transaction
    •	Rollback inner transaction → outer can continue
    ________________________________________
    d) SUPPORTS
    @Transactional(propagation = Propagation.SUPPORTS)
    public User readUser() {
        return findUser();
    }
    •	Runs inside existing transaction if present
    •	Otherwise executes non-transactionally (safe for read-only)
    ________________________________________
    e) NOT_SUPPORTED
    @Transactional(propagation = Propagation.NOT_SUPPORTED)
    public void externalCall() {
        callExternalAPI(); // runs outside any existing transaction
    }
    ________________________________________
    f) MANDATORY / NEVER
    @Transactional(propagation = Propagation.MANDATORY)
    public void mustRunInTx() { ... }

    @Transactional(propagation = Propagation.NEVER)
    public void mustRunOutsideTx() { ... }
    •	Throws IllegalTransactionStateException if rules not satisfied
    ________________________________________
    4️⃣ How Spring Handles Propagation Internally
    1.	Proxy intercepts method call
    2.	TransactionInterceptor checks propagation type
    3.	PlatformTransactionManager:
    o	Create new transaction
    o	Join existing transaction
    o	Suspend existing transaction
    4.	Commit / rollback at method exit
    5.	Savepoints used for NESTED propagation
    ________________________________________
    5️⃣ Key Points for Microservices / Real Apps
    •	REQUIRED → most service-to-service calls
    •	REQUIRES_NEW → independent logging, audit, messaging
    •	NESTED → complex workflows needing partial rollback
    •	SUPPORTS / NOT_SUPPORTED → read-only or non-transactional integration
    •	MANDATORY / NEVER → enforce strict transaction boundaries


5.	Isolation levels mapping to DB.
    1️⃣ What is Transaction Isolation?
    Isolation level determines how one transaction is isolated from others, controlling visibility of uncommitted or concurrent data changes.
    ________________________________________
    2️⃣ Spring / JDBC Isolation Levels
    Level	Spring Constant	Meaning	Typical DB Behavior	Issues Prevented
    READ_UNCOMMITTED	Isolation.READ_UNCOMMITTED	Can read uncommitted changes from other transactions	MySQL: READ UNCOMMITTED	Prevents nothing; allows dirty reads, non-repeatable reads, phantoms
    READ_COMMITTED	Isolation.READ_COMMITTED	Reads only committed data	Oracle/MySQL/Postgres: READ COMMITTED	Prevents dirty reads, allows non-repeatable reads and phantoms
    REPEATABLE_READ	Isolation.REPEATABLE_READ	Ensures repeated reads see same data	MySQL: REPEATABLE READ (InnoDB), Postgres: REPEATABLE READ	Prevents dirty reads and non-repeatable reads, allows phantoms
    SERIALIZABLE	Isolation.SERIALIZABLE	Full isolation, transactions appear sequential	All DBs: SERIALIZABLE	Prevents dirty reads, non-repeatable reads, phantoms; highest locking/serialization
    ________________________________________
    3️⃣ Common Phenomena
    Phenomenon	Meaning	Which isolation levels prevent it
    Dirty Read	Read uncommitted data	READ_COMMITTED+
    Non-repeatable Read	Same query returns different results in same tx	REPEATABLE_READ+
    Phantom Read	New rows added by another tx appear in repeated query	SERIALIZABLE
    ________________________________________
    4️⃣ DB-Specific Notes
    a) MySQL InnoDB
    •	Default: REPEATABLE READ
    •	Uses MVCC → no read locks for reads
    •	SERIALIZABLE → applies gap locks, prevents phantoms
    b) Oracle
    •	Default: READ COMMITTED
    •	MVCC-based → consistent reads
    •	Serializable → serial execution behavior
    c) PostgreSQL
    •	Default: READ COMMITTED
    •	REPEATABLE READ → snapshot isolation, prevents non-repeatable reads
    •	SERIALIZABLE → detects conflicts, may rollback transactions
    •	6️⃣ Mapping Table Summary
    Spring Isolation	JDBC Constant	DB Mapping	Prevents
    READ_UNCOMMITTED	Connection.TRANSACTION_READ_UNCOMMITTED	MySQL/Oracle/Postgres	Nothing
    READ_COMMITTED	Connection.TRANSACTION_READ_COMMITTED	MySQL/Oracle/Postgres	Dirty reads
    REPEATABLE_READ	Connection.TRANSACTION_REPEATABLE_READ	MySQL/Postgres	Dirty + Non-repeatable reads
    SERIALIZABLE	Connection.TRANSACTION_SERIALIZABLE	All	Dirty + Non-repeatable + Phantom reads


6.	Why rollback doesn’t happen for checked exceptions?
    2️⃣ Why This Design Choice?
    1.	Unchecked exceptions usually indicate a programming error or unexpected failure
    o	e.g., NullPointerException, IllegalArgumentException
    o	Rollback makes sense → data might be inconsistent
    2.	Checked exceptions usually indicate expected, recoverable situations
    o	e.g., IOException, ParseException
    o	By default, Spring assumes the caller can handle it → rollback not automatic
    3.	Flexibility
    o	Developers can explicitly configure rollback rules using rollbackFor
    3️⃣ How to Rollback for Checked Exceptions
    Option 1: Use rollbackFor
    @Transactional(rollbackFor = IOException.class)
    public void process() throws IOException {
        saveData();
        throw new IOException("Rollback required");
    }
    •	Now Spring will rollback even for this checked exception
    Option 2: Use rollbackForClassName
    @Transactional(rollbackForClassName = "java.io.IOException")


7.	Nested transaction – how it actually works?
       A nested transaction is a sub-transaction inside a parent transaction.
       If the nested transaction fails, only the nested part rolls back, but the outer transaction can still commit.
       •	Spring propagation type: Propagation.NESTED
       •	Requires underlying JDBC / database support for savepoints
       2️⃣ How It Differs From REQUIRES_NEW
       Feature	NESTED	REQUIRES_NEW
       Parent transaction	Active	Suspended
       Child failure	Rollback to savepoint; parent can continue	Full independent rollback; parent unaffected
       Resource usage	Same connection	Separate connection / transaction
       Use case	Partial rollback inside transaction	Independent auditing, logging, or messaging
       ________________________________________
       3️⃣ Internal Mechanics
       Step 1: Parent Transaction Starts
       @Transactional
       public void processOrder() {
           createOrder();
           applyDiscount(); // NESTED transaction
       }
       •	Spring opens parent transaction
       •	JDBC Connection bound to thread
       •	Transaction manager tracks TransactionStatus
       ________________________________________
       Step 2: Nested Transaction Begins
       @Transactional(propagation = Propagation.NESTED)
       public void applyDiscount() { ... }
       •	Spring checks existing transaction → parent exists
       •	Instead of creating a new DB transaction, Spring creates a savepoint:
       savepoint = connection.setSavepoint("nested-1");
       •	Nested operations now use the same connection, but rollback is limited to the savepoint
       ________________________________________
       Step 3: Nested Transaction Fails
       •	If exception occurs in nested method:
       connection.rollback(savepoint);
       •	Only changes after the savepoint are rolled back
       •	Parent transaction remains active
       •	Outer transaction can continue:
       commit parent transaction → persists all other changes
       ________________________________________
       Step 4: Nested Transaction Succeeds
       •	No rollback occurs
       •	Changes merge seamlessly with parent transaction
       •	Commit occurs when parent transaction commits
       ________________________________________
       4️⃣ Visual Flow
       Parent Tx start
         |-- Nested Tx start → savepoint created
         |-- Nested Tx fails → rollback to savepoint
       Parent Tx continues
       Parent Tx commit → commits everything except rolled-back nested part


8.	What happens if two transactional methods call each other?
    1️⃣ The Scenario
    @Service
    public class MyService {

        @Transactional
        public void methodA() {
            // some logic
            methodB(); // also @Transactional
        }

        @Transactional
        public void methodB() {
            // transactional logic
        }
    }
    •	methodA calls methodB inside the same class
    •	Both are annotated @Transactional
    ________________________________________
    2️⃣ What Actually Happens Internally
    •	Spring uses AOP proxies to intercept @Transactional calls
    o	Can be JDK dynamic proxy or CGLIB proxy
    •	The proxy intercepts external calls to the bean
    •	Self-invocation (internal call) bypasses the proxy
    o	methodB() is called directly, no transaction advice applied
    •	So methodB runs in the same transaction as methodA, ignoring its own @Transactional settings
    ________________________________________
    3️⃣ Consequences
    Scenario	Result
    Same bean, self-invocation	methodB does not create a new transaction or use its propagation settings
    Different bean, external call	@Transactional applied as expected
    •	REQUIRES_NEW inside self-invocation will not start a new transaction
    •	Only works if call goes through Spring proxy
    ________________________________________
    4️⃣ How Spring Handles Transactions Internally
    Caller → Proxy → TransactionInterceptor → PlatformTransactionManager → DB
    •	External call → intercepted by proxy → transaction advice applied
    •	Internal call → direct method call → no proxy → no interception → uses existing transaction context
    ________________________________________
    5️⃣ How to Fix / Workaround
    Option 1: Extract to another Spring-managed bean
    @Service
    public class AnotherService {
        @Transactional
        public void methodB() { ... }
    }

    @Service
    public class MyService {
        @Autowired
        private AnotherService anotherService;

        @Transactional
        public void methodA() {
            anotherService.methodB(); // passes through proxy
        }
    }
    •	Now methodB is properly intercepted
    Option 2: Use ApplicationContext to get proxy
    @Autowired
    private ApplicationContext context;

    @Transactional
    public void methodA() {
        context.getBean(MyService.class).methodB(); // goes through proxy
    }
    •	Less clean, but works


9.	Why transaction doesn’t work in same class?
    1️⃣ How Spring Applies @Transactional
    •	Spring does not modify your method code directly
    •	Instead, it uses AOP proxies (JDK dynamic proxies or CGLIB) to intercept method calls
    •	The proxy wraps the bean and applies transaction advice:
    Caller → Proxy → TransactionInterceptor → PlatformTransactionManager → DB
    •	Only calls going through the proxy trigger the transactional behavior
    ________________________________________
    2️⃣ What Happens in the Same Class
    @Service
    public class MyService {

        @Transactional
        public void methodA() {
            methodB(); // calls methodB internally
        }

        @Transactional
        public void methodB() {
            // transactional logic
        }
    }
    •	methodA() calls methodB() directly on this
    •	This does not go through the Spring proxy
    •	methodB() is not intercepted, so its @Transactional does nothing
    •	methodB() executes in the same transaction as methodA (or no transaction if methodA is not transactional)
    ________________________________________
    3️⃣ Why This Happens
    1.	Spring AOP is proxy-based (by default)
    2.	Proxies intercept external calls, not internal calls
    3.	Self-invocation bypasses the proxy → no advice applied
    This is true for all AOP-based annotations, not just @Transactional
    ________________________________________
    4️⃣ Workarounds
    a) Extract the method to another Spring-managed bean
    @Service
    public class AnotherService {
        @Transactional
        public void methodB() { ... }
    }

    @Service
    public class MyService {
        @Autowired
        private AnotherService anotherService;

        public void methodA() {
            anotherService.methodB(); // goes through proxy
        }
    }
    •	Now methodB() is properly intercepted
    ________________________________________
    b) Use the Spring proxy of the same bean
    @Autowired
    private ApplicationContext context;

    public void methodA() {
        context.getBean(MyService.class).methodB(); // calls through proxy
    }
    •	Works but less clean
    •	Avoids creating another bean
    ________________________________________
    c) Avoid calling private methods
    •	Only public methods are proxied
    •	private methods cannot be intercepted by Spring AOP


10.	How to force rollback for checked exception?
    In Spring transactions, by default, only unchecked exceptions (RuntimeException) trigger rollback. Checked exceptions (Exception) do not. But you can force rollback for checked exceptions using @Transactional configuration. Let’s break it down step by step.
    ________________________________________
    1️⃣ Using rollbackFor
    @Transactional(rollbackFor = IOException.class)
    public void processFile() throws IOException {
        // some DB operations
        throw new IOException("Force rollback");
    }
    ✅ Here, even though IOException is checked, Spring rolls back the transaction.
    •	rollbackFor can take multiple exception classes:
    @Transactional(rollbackFor = {IOException.class, SQLException.class})
    ________________________________________
    2️⃣ Using rollbackForClassName (Alternative)
    @Transactional(rollbackForClassName = "java.io.IOException")
    public void processFile() throws IOException {
        throw new IOException();
    }
    •	Useful if you only know exception class by name, not type
    ________________________________________
    3️⃣ Difference Between rollbackFor and noRollbackFor
    Attribute	Behavior
    rollbackFor	Forces rollback for specified exception(s), even checked
    noRollbackFor	Prevents rollback for specified exception(s), even unchecked
    @Transactional(rollbackFor = IOException.class, noRollbackFor = MyBusinessException.class)

advantage and disadvange of spring
===========================================================
✅ Advantages of Spring Framework
1. Loose Coupling via Dependency Injection (DI)
•	Objects depend on interfaces, not implementations.
•	Easy to swap implementations without code change.
Why it matters:
•	Better testability
•	Cleaner architecture
•	Supports SOLID principles
________________________________________
2. Inversion of Control (IoC) Container
•	Spring manages object creation, lifecycle, and wiring.
•	Centralized configuration via annotations / Java config / XML.
Real-world benefit:
•	Reduces boilerplate factory code
•	Consistent object lifecycle management
________________________________________
3. Aspect-Oriented Programming (AOP)
•	Clean separation of cross-cutting concerns:
o	Logging
o	Transactions
o	Security
o	Auditing
Without Spring AOP:
•	Code duplication across layers.
________________________________________
4. Transaction Management
•	Declarative transactions using @Transactional
•	Works across JDBC, JPA, Hibernate, JMS.
Enterprise advantage:
•	Consistent transaction handling
•	Less error-prone than manual transaction code
________________________________________
5. Modular Architecture
•	Use only what you need:
o	Core
o	Context
o	AOP
o	ORM
o	MVC
o	Security
Benefit:
•	Flexible and extensible.
________________________________________
6. Abstraction Over APIs
•	Simplifies integration with:
o	JDBC
o	JPA / Hibernate
o	JMS
o	Cache providers
Example:
JdbcTemplate
•	Eliminates repetitive try-catch & resource handling.
________________________________________
7. Strong Ecosystem & Community
•	Spring MVC, Security, Data, Batch, Integration.
•	Industry standard for Java enterprise apps.
________________________________________
8. Test-Friendly
•	Supports unit & integration testing.
•	Easy mocking with DI.
________________________________________
❌ Disadvantages of Spring Framework
1. Steep Learning Curve
•	Concepts to master:
o	IoC
o	DI
o	Bean lifecycle
o	Proxies & AOP
o	Transaction propagation
Common junior pain point:
•	“Where is this object coming from?”
________________________________________
2. Configuration Complexity (Without Boot)
•	Requires significant manual configuration.
•	XML / Java config can become verbose.
Compared to Spring Boot:
•	More setup, slower initial development.
________________________________________
3. Runtime Overhead
•	Uses:
o	Reflection
o	Proxies
o	Dynamic bean wiring
Impact:
•	Slight performance and memory overhead.
________________________________________
4. Debugging Can Be Hard
•	Issues often occur during startup.
•	Stack traces can be long and complex.
________________________________________
5. Not Ideal for Simple Applications
•	Overkill for small utilities or scripts.
•	Lightweight frameworks may be better.
________________________________________
6. Magic / Hidden Behavior
•	Heavy use of annotations and conventions.
•	Behavior not always obvious from code alone.
